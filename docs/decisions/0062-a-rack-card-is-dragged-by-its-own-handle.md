# 0062. A rack card is dragged by its own handle, and the arrow keys on that handle are the keyboard path

- **Date:** 2026-08-16
- **Status:** accepted

P34 proposed dnd-kit for the rack's reorder. It is refused: a new dependency needs approval (principle 7) and none was available, and the repo already authors pointer gestures in one idiom — pointer capture on the grip, a `useRef` drag record, candidate positions written straight to the elements, one command on release (`src/ui/LoopHandles.tsx`, `src/ui/Knob.tsx`). `src/ui/rackDrag.ts` is that idiom applied to a vertical list: a card's centre is measured against where its neighbours started, the cards it passes shift by its own outer height, and the release sends `effect.reorder` with the index it landed on — the same command the two arrow buttons sent, so `./scripts/drive` reaches reordering unchanged. The gesture is captured by and answered on the list, not on the grip that started it, because a card can leave under a live drag (an undo, a removal from the driver) and a handler on the card it took with it would never run; for the same reason the release re-reads the store and commits nothing if the rack is no longer the list the gesture measured. A library would have brought its own event model, its own accessibility story and its own sensors for a rack that is one column of a handful of cards.

The `earlier`/`later` buttons went with it, and with them the `earlier` and `later` entries in `ACTION_ICONS`. **The keyboard path they were survives on the handle**: the handle is a focusable button, and ArrowUp/ArrowDown on it send the same `effect.reorder` one slot at a time. A press at either end takes the key and sends nothing — `reorderEffect` would clamp an out-of-range index back onto the slot the card already occupies, and the handle owning the arrows is what keeps the page from scrolling under a key that did nothing. That is one control per card rather than two, it is where a pointer already aims, and it is what the browser smoke checks — a pointer drag cannot prove a keyboard path is reachable, so the keyboard is the one the gate spends its time on.
